Catalog search — rotation location instead of call number

A release in rotation is not on the stacks: its call number sends a DJ to a shelf slot that's empty. For actively-rotating rows, both experiences' search results swap the call-number cell for the record's real location — rotation bin + card. Everything else about the results is unchanged.

Try it: flip the flag to compare today's display with the new one; search pratt, duke, or yanya; hover a blue location pill to see the card's name.

What the annotations mean

  • 1AlbumSearchResult.rotation_bin is already the CURRENT_DATE-filtered value — non-null means actively rotating, today. The new card field rides the same JOIN with the same filter (S1 contract + B6 emission), so a killed row can never point at a card it left.
  • 2The swap itself (decision 6): a rotating row's call-number cell shows bin + card in place of lettercode numbercode/entry. The call number isn't shown at all — displaying both would still send DJs to the stacks. Non-rotating rows are untouched.
  • 3The card's optional name travels as a title tooltip on the location pill, not as columns — search results stay scannable, and an unnamed card needs no empty space reserved.
  • 4The modern bin chip in ReleaseChips already exists and stays — it marks rotation membership at a glance; the location pill answers the different question "where do I physically find it." Only the call-number cell changes (D10).
  • 5Classic gets the identical swap in its Code column (SearchResults.tsx), rendered in the JSP's own idiom — bold text, no pill chrome. The card field threads through convertToAlbumEntry, a hand-maintained mapping in the same drift class as RotationListRow.
  • 6Flag-gated with the same NEXT_PUBLIC_ROTATION_ADMIN_ENABLED flag as the admin area: until the card backfill (B7) and MD adoption, cards carry no signal — the search display flips together with the admin launch (D7). Flip the switch to see today's behavior.
