Rotation age & card staleness

Answering the MD ask: "some way for the site itself to be like 'hey!, [x] album has been in Medium 7 [for] [x] days' or 'Light 6 has not been updated in [x] days'." Two separate features on two existing surfaces — per-record age on the Rotation list, and per-card last activity on the Cards tab — plus the station policy that decides what counts as overdue. Nothing here is a new page.

Annotations

n design note    n costs backend work — everything else is dj-site only

  1. 1Both features land on surfaces that already exist and are already live in prod (NEXT_PUBLIC_ROTATION_ADMIN_ENABLED, on since 2026-09-15). No new route, no new nav entry.
  2. 2The age figure is free. Every row from GET /library/rotation?status=all already carries rotation_add_date, and RotationAdminList.tsx already renders it as a bare added 07/28/26. This replaces that with elapsed days. A bin move is add-then-kill (addThenRetire.ts) — a new row with a fresh add_date — so "days in Heavy" is exactly right, not an approximation.
  3. 3Sorting is the quietest possible version of "hey!": put the oldest record at the top and the question answers itself every time an MD opens the page. Client-side over the one read the list already does; add_date is unindexed on rotation, which doesn't matter at ~125 active rows but would if this ever moved server-side.
  4. 4Card dwell time is not derivable. Card reassignment within a bin is a plain card_id PATCH — no timestamp, no history — and rotation_cards is (id, bin, number, name) with no dates at all. So for a record that has been shuffled between cards, "84 days on Medium 1" is unknowable; the honest answer is the bin figure with the ambiguity marked (hover the Duke Ellington row). If the MDs need the literal card number, that's a card_assigned_at column on rotation — Backend-Service work, not dj-site.
  5. 5Card last-activity is max(add_date, kill_date) across the rows carrying that card_id. Killed rows keep their card_id in the database — the kill writer doesn't null it, only the catalog-search projection blanks card for killed rows — so removals count as work done, not just adds. Derivable client-side from the same status=all read the list already holds.
  6. 6The tidier version serves last_activity next to the existing active_count on GET /library/rotation/cards, so the Cards tab stops depending on the list's read. Worth doing only if the client-side derivation proves awkward — ship without it first.
  7. 7The thresholds are the part engineering can't supply. "Overdue" is a policy number per bin, and the MDs own it. Hard-coding a guess would produce a surface that cries wolf and gets ignored, which is worse than no surface.
  8. 8Three nudge treatments, because "be like hey!" spans a wide range. Quiet is age text plus sort — no judgement, nothing to dismiss. Flagged marks overdue rows and counts them. Loud names them in a banner at the top of the page. There is no push channel for MDs in dj-site today, so a real notification (email, Slack) is a separate, larger piece of work — these three are all reachable now.
  9. 9The play count on each row is library.plays — the album's lifetime total, not spins during this rotation stint. It reads like the "is this record working?" signal and isn't: a reissue can show hundreds of plays from twenty years ago. Shown greyed here precisely so nobody wires a decision to it. A real spins-since-filed figure needs a flowsheet range query, the shape lib/features/rotation-tally/tally.ts already does weekly.
  10. 10This isn't hypothetical maintenance. Backend-Service#2184 found 196 rotation records added before 2026 and never killed — oldest 2004-12-20, one titled test / test sitting in Heavy since 2008 — because label-less records failed a join in the old tubafrenzy admin and were invisible to the person who kills them. No rotation predicate has an age bound, so all 196 read as current rotation and badged live plays on dj-site. An age column is the instrument that surfaces exactly that.
