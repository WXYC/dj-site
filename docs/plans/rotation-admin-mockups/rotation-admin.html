Rotation Admin

The bench is the way rotation items are created, living in its own Rotation Admin area of the admin interface. Three views: Add to rotation (create), the Rotation list (manage), and Cards — because bins subdivide into numbered cards (1…N per bin, each optionally named), a fact modeled nowhere in the system today. Every rotation item lives on a card within its bin.

▶ Live demo — type "nil", pick Nilüfer Yanya, note the card picker under the bin (defaults to the bin's newest card; ＋ adds one) and the URLs field (＋ adds rows, − removes), file it, then follow "view in Rotation list". There: search + bin chips; filtering to one bin reveals its card sub-filter; each row's card is a dropdown (plain edit). The Cards tab renames, adds, and deletes cards.

Annotations

  1. 1Three routes in one admin area: /dashboard/admin/rotation/new (create), /dashboard/admin/rotation (manage), /dashboard/admin/rotation/cards (structure), gated by RequireMD. The catalog page keeps no Add Release button — filing is an admin task, searching is everyone's.
  2. 2One pass, one submit: match-or-create the artist, file the release, add the rotation entry to a bin and card — the runRotationImport-style chain. Missing fields outline in red; success links straight to the list view.
  3. 3The code number fills itself from the peek (GET /library/artists/peek-code) and re-syncs until you type your own value; the conflict check guards the override. End state: server-side assignment (code_number optional on POST /library/artists) and this field disappears.
  4. 4The bin defaults to Heavy (DEFAULT_BIN); deselecting files library-only, so the bench still covers plain cataloging without a separate button anywhere.
  5. 5Kill = killRotationEntry; Unkill = updateRotationRow({kill_date: null}); moving between bins is add-then-kill (no endpoint edits a bin) and lands on the target bin's newest card. The Killed section assumes the catalogued+killed read gets built (today's backend can't list those rows).
  6. 6The session ledger stays on the add view — batch receipt and partial-failure retry for this sitting, distinct from the full rotation list. A transactional POST /library/file would collapse it to a plain receipt.
  7. 7Search matches artist, title, and shelf code (diacritic-insensitive) and composes with the bin chips; both narrow the Killed section too. Filtering to a single bin reveals that bin's card chips as a sub-filter — pull one card's worth of records at a glance. All client-side over the single GET /library/rotation read.
  8. 8Cards are net-new modeling: bins subdivide into cards numbered 1…N per bin, each optionally named, and every rotation item lives on one. Assignment defaults to the bin's newest card (where new records physically go); ＋ adds card N+1 and selects it — name it later in the Cards tab. Within a bin, a row's card is a plain field edit (the dropdown on each list row → PATCH /library/rotation/:id gains card), unlike bin moves.
  9. 9Card management: rename inline (names are optional), add card N+1, delete only the last card and only when empty — numbering stays contiguous 1…N, a spec decision to confirm. Backend shape: a rotation_cards table (bin, number, name) plus a card column on rotation rows — net-new schema, Backend-first per the tubafrenzy Phase 1 freeze (no new legacy sync for new data).
  10. 10Optional URLs travel with the rotation entry (Bandcamp, Discogs, …). The ＋ at the end of the field adds another row; a − appears on every row once there's more than one. Empty rows are dropped on submit; filed links surface as the 🔗 count on the list row (hover for the URLs). Backend: a URLs child table (or array column) on the rotation row — net-new, like cards.
