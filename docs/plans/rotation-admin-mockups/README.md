# Rotation admin mockups

Interactive HTML mockups (2026-09-13) for the rotation filing redesign proposed in [`../catalog-filing-bench.md`](../catalog-filing-bench.md). Open `index.html` in a browser from disk; every page is self-contained (vanilla JS, no build, no network) and simulates against a small in-memory library seeded with canonical WXYC fixture data. Each page carries numbered annotations tying the design to existing code and endpoints.

**`rotation-admin.html` is the current direction** — it supersedes the plan doc where they differ. The decisions it encodes: the bench is *the* way rotation items are created and lives in the admin interface as its own Rotation Admin area ("Catalog Admin" is already the format/genre admin page) (no Add Release button on the catalog page, which stays a read/search surface); creation, the rotation list, and card management are three separate views; the rotation list gets search + bin filters + a per-bin card sub-filter, Kill/Unkill, bin moves via add-then-kill, and per-row card reassignment; the artist code number auto-fills from the peek endpoint (no accept button); rotation bins subdivide into numbered, optionally-named **cards** (1…N per bin — net-new modeling, nowhere in the system today); rotation entries carry optional **URLs** (dynamic +/− rows).

**`catalog-search-rotation.html`** is the companion current-direction page for the DJ-facing consequence (decision 6 in the [Rotation Admin epic, dj-site#1480](https://github.com/WXYC/dj-site/issues/1480)): catalog search results must not show the library call number for an actively-rotating release — the record isn't on the stacks, and the call number sends DJs there — so both experiences swap that cell for the rotation **bin + card** (card name as tooltip), gated behind the same flag as the admin area. The page's flag toggle compares today's display with the new one.

**`rotation-age.html`** is a later proposal (2026-09-24), from an MD request for the site to flag what needs replacing: *"some way for the site itself to be like 'hey!, [x] album has been in Medium 7 [for] [x] days' or 'Light 6 has not been updated in [x] days'."* It adds two things to surfaces that already exist rather than proposing a new one — per-record **age** on the Rotation list (elapsed days replacing today's bare `added 07/28/26`, plus sort-by-oldest and a per-bin replacement window) and per-card **last activity** on the Cards tab (`max(add_date, kill_date)` over the card's rows, so a kill counts as work). A treatment switcher compares three volumes of nudge: quiet (age + sort), flagged (marked and counted in place), loud (named in a banner). Two honest limits are marked in the page rather than designed around: the age figure is exact for a **bin** (a bin move is add-then-kill, so `add_date` restarts) but **card dwell time is not derivable at all** — card reassignment is an untimestamped `card_id` PATCH and `rotation_cards` carries no dates — and the thresholds are station policy the MDs have to supply, not a number engineering can pick. Background: Backend-Service#2184, where 196 pre-2026 rotation records were never killed because they were invisible to the person who kills them.

**`card-assignment.html`** (2026-09-28) mocks B3 ([dj-site#1674](https://github.com/WXYC/dj-site/issues/1674)) from the [rotation age epic, dj-site#1663](https://github.com/WXYC/dj-site/issues/1663): the card assignment panel for the one-time re-carding pass. When Rotation Admin launched, migration 0165 put every active record on card 1 of its bin, and the only way to move them was the Rotation list's per-row select. The panel opens from a card on the Cards tab and lists that bin's active records (read with `status=active`, never `status=all`). The MD ticks what is physically on the card; records already there are locked, so every save is a set of moves *onto* the open card. A **Still on Heavy 1** filter narrows to the backfill pile, and **Save & open** the next card makes the pass a walk along the shelf. Saving is one batch mutation over the existing per-row PATCH: it refetches once when the batch settles (the page's request counter shows it) and reports a per-record result with a retry for failures, since the writes are not transactional. Cards are named the way MDs say them ("Heavy 3"), and the page stays plain because Sam confirmed cards change one record at a time; this is a one-time tool, not the day-to-day path.

The numbered pages (`1-`…`5-`) are the earlier strategy explorations that fed the direction; `index.html` records each one's disposition (evolved / folded in / rejected / parked / superseded). They're kept as the decision trail, not as live proposals.
